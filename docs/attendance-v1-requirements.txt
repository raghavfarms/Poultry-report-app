Poultry Reporting System
Attendance & Workforce Management Module — Version 1
1. Project Context
This Attendance module must be developed inside the existing MERN Poultry Reporting System.
Existing technology:
Frontend:
React + Vite

Backend:
Node.js + Express

Database:
MongoDB + Mongoose

Authentication:
JWT

Existing Firms:
1. Raghav
2. Sanjana

The Attendance module must use the existing:
Firm collection
User authentication
Admin system
Application layout
Sidebar
API architecture
MongoDB connection

The module must be isolated cleanly so an Attendance error does not break Diesel, Transport or other modules.

2. V1 Main Business Goal
Management should be able to answer these questions immediately:
Who are our workers?

Which firm does each worker belong to?

Which shed/work location is each worker assigned to?

Who came to work today?

What time did each worker enter?

Who is currently inside the farm?

Which shed is each present worker assigned to?

How many workers are currently present in each shed?

What time did each worker leave?

How many hours did each worker work?

Who is absent/not reported?

Was a worker transferred to another shed?

Was a worker transferred to another firm?

Where was a worker deployed historically?

Has anyone manually corrected attendance?

12. Critical Deployment Rule
Never simply overwrite historical deployment.
WRONG:
worker.shed = newShed

if that destroys previous assignment history.
CORRECT:
Existing deployment:
effectiveTo = transferDate

Create new deployment:
effectiveFrom = transferDate
effectiveTo = null

Example:
Raj Kumar

01 Sep → 07 Sep
Raghav / Shed 1

08 Sep → Present
Raghav / Shed 3

Both records remain permanently available.

24. Server Timestamp
Do not trust a timestamp manually sent by the browser for normal online attendance.
For live online attendance:
Backend/server creates timestamp

Store timestamps consistently, preferably UTC internally.
Display them in the farm/user timezone.

25. Duplicate Scan Protection
This is mandatory.
Example:
08:00:00 → DUTY IN ✅

08:00:05 → Worker scanned again

Do NOT convert the second scan immediately into OUT.
Return:
Attendance already marked.
Duplicate scan detected.

Use a configurable duplicate-scan protection window.

26. IN/OUT State Protection
Prevent impossible states.
Do not allow:
DUTY_OUT without DUTY_IN

Do not allow:
DUTY_IN
DUTY_IN

for the same active attendance session.
Do not allow accidental:
DUTY_OUT
DUTY_OUT


27. Face Not Recognized
If no reliable worker match exists:
FACE NOT RECOGNIZED

No attendance should be written.
Allow operator to retry.

28. Attendance Transaction
Attendance records should be immutable transactions where practical.
Recommended structure:

workLocation

eventType

source
createdAt

Source:

MANUAL
CORRECTION

Snapshots are useful because future master changes should not corrupt historical reports.

54. MongoDB Indexes
Indexes should be designed before production.
Examples:
Worker:
{ workerCode: 1 } unique

WorkerDeployment:
{ worker: 1, effectiveFrom: -1 }

Attendance:
{ worker: 1, attendanceDate: 1 }

Attendance:
{ firm: 1, attendanceDate: 1 }

Attendance:
{ firm: 1, timestamp: -1 }

WorkLocation:
{ firm: 1, active: 1 }

Exact indexes should follow final schema/query design.

55. Database Uniqueness / Race Protection
Important attendance rules should be protected at database/backend level where possible.
Do not rely only on:
"button disabled"

Two simultaneous API requests should not accidentally create two Duty IN records.

56. MongoDB Transactions
Use transactions where multiple related writes must either all succeed or all fail.
Especially consider for:
Closing old deployment
+
Creating new deployment

or other multi-document critical updates.

57. Do Not Store Huge Base64 Images in Worker Documents
Avoid:
worker.faceImage = massiveBase64String

Store files/face assets appropriately and keep references/metadata in MongoDB.
Keep normal MongoDB worker documents lightweight.

58. Face Data Security
Face templates/embeddings are sensitive data.
V1 should at minimum:
Restrict access
Do not expose descriptors in normal Worker APIs
Do not send all templates unnecessarily to regular users
Protect face registration endpoints
Prevent non-admin modification

72. V1 Definition of Done
Version 1 is complete only when the following full scenario works reliably:
1. Admin logs in.

2. Admin creates Raghav sheds.

3. Admin creates Sanjana sheds.

4. Admin creates designations.

5. Admin creates worker Raj Kumar.

6. Raj is assigned:
   Raghav → Shed 3 → Farm Worker → Supervisor A.

7. Admin registers Raj's face.

8. Raj comes in the morning.

9. Operator scans Raj's face.

10. System recognizes Raj.

11. Backend validates Raj.

12. System stores:
    DUTY IN = exact time.

13. Raj appears as PRESENT.

14. Raghav present count increases.

15. Shed 3 live count increases.

16. Raj's name appears inside Shed 3 worker list.

17. Raj accidentally scans again immediately.

18. Duplicate scan is rejected.

19. Raj comes at departure time.

20. Face is scanned again.

21. System recognizes Raj.

22. System creates DUTY OUT.

23. Working hours are calculated.

24. Raj becomes DUTY COMPLETED.

25. Raj disappears from current-inside count.

26. Daily report shows correct IN, OUT and hours.

27. Monthly report includes that day.

28. Admin can view Raj's attendance history.

29. Admin transfers Raj from Shed 3 → Shed 4.

30. Old deployment remains in history.

31. New attendance uses Shed 4.

32. Old attendance continues showing Shed 3.

33. If attendance is incorrect, Admin can correct it.

34. Original/corrected information remains in audit history.

35. Diesel and Transport modules continue working normally.

If all 35 scenarios work correctly, Attendance V1 is ready for controlled production use.
